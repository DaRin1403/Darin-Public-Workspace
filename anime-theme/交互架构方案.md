# Kaguya 皮肤 · 交互界面架构方案 v0.1

> 目标：**看到一个界面元素 → 立刻知道它在代码里的位置 → 快速准确地改它。**
> 本文档只做架构提案与可行性验证，不改动任何实际代码与颜色。

---

## 一、核心模型：层级 × 界面的二维绑定网络

### 1.1 竖直轴（列）= 交互单元链（表头）

每个**可交互单元**（一个按钮）是一根"柱子"，从它往下长出它的弹出链：

```
按钮本体(L0) → 一级菜单(L1) → 二级菜单(L2) → 三级菜单(L3) → 四级菜单(L4)
```

一根柱子上的所有层级，代码里应能沿一条"链"找到（按类名前缀/规则块相邻）。

### 1.2 水平轴（行）= 层（Layer）

同一个界面（surface）里，**所有柱子的同一级浮层属于同一层**：

```
一个界面上：
  行0 = 所有按钮本体（常驻层）
  行1 = 所有一级菜单（同一层视觉配方、同一 z-index 带）
  行2 = 所有二级菜单
  行3 = 所有三级菜单
  …
```

**关键收益**：同层的视觉配方统一（如所有 L1 菜单面板共用同一套粉玻璃参数），改一层 = 改一个变量，不用逐按钮改。

### 1.3 分界面（surface）

统一架构之下按位置分 8 个界面，对应代码里的"══ 分区 ══"横幅：

| 编号 | 界面 | 代码定位 |
|---|---|---|
| S1 | 输入区（输入框卡片及其弹出） | 搜 `分区：输入区` |
| S2 | 对话区（消息流） | 搜 `分区：对话区` |
| S3 | 上边栏（顶部标题栏） | 搜 `分区：上边栏` |
| S4 | 左边栏（侧栏） | 搜 `分区：左边栏` |
| S5 | 设置区（设置浮层/插件页） | 搜 `分区：设置区` |
| S6 | 轨迹区（表格/工具栏/时间线） | 搜 `分区：轨迹区` |
| S7 | 轨迹详情区（右侧详情面板） | 搜 `分区：轨迹详情区` |
| S8 | 全局（跨界面共享） | 搜 `分区：全局` |

## 二、层级定义（Level 语义，全皮肤统一）

| 层 | 名称 | 定义 | 视觉配方（现状） |
|---|---|---|---|
| L0 | 常驻层 | 界面上的按钮本体，静止/悬停/按下三态 | A/B/C/D 四类按钮配方 |
| L0.5 | 悬浮提示层 | Tooltip（短暂悬浮，可出现在任何层之上） | 淡粉玻璃 + 白边 |
| L1 | 一级菜单层 | 点按钮弹出的第一层浮层（菜单/面板/弹窗） | 粉玻璃面板 78%/55% + blur 10 |
| L2 | 二级菜单层 | 从 L1 里再点出的浮层/子面板 | 同 L1 配方或浅一档 |
| L3 | 三级菜单层 | 从 L2 再点出 | 浅粉面板 + 深粉选项 |
| L4 | 四级菜单层 | 最深一级 | 保留扩展位 |

**层级判定口诀**：弹了几次出来的，就是几级菜单；按钮本体永远是 L0；悬浮提示是 L0.5。

## 四、代码组织落地方式（提案，不改动）

### 4.1 现状（已就位）
- 29 个 `══ 分区 ══` 横幅 = 水平轴的 surface 维度 ✅；
- 每条规则块带注释 = 竖直轴的单元定位 ✅。

### 4.2 待补（建议下一阶段）
1. **每条规则块注释追加层级标记**：如 `/* L1 模型菜单面板 */`——搜 `L1` 就能列出全皮肤所有一级菜单；
2. **同层配方变量化**（沿用 `--kaguya-hover` 的思路）：
   ```
   --kaguya-l1-panel   (所有一级菜单面板背景)
   --kaguya-l1-item    (所有一级菜单条目悬停)
   --kaguya-l2-panel   (所有二级菜单面板)
   --kaguya-title      (标题块深粉)
   --kaguya-body       (正文中粉)
   --kaguya-recess     (第三层下凹)
   ```
   改"所有一级菜单"= 改一个变量；改"某一个按钮"= 改该单元规则块。
3. **查找流程标准化（五步）**：
   ```
   ① 看界面 → 定 surface（S1~S8，对应分区横幅）
   ② 看元素 → 定单元（按钮类名）
   ③ 看弹出关系 → 定层级（L0 常驻 / L1 一级菜单 / L2 二级…）
   ④ 搜“分区 + 类名” → 定位规则块
   ⑤ 全局改配方 → 变量；单点改 → 该块
   ```

## 五、特例与例外清单（架构必须容纳）

| # | 特例 | 处置原则 |
|---|---|---|
| 1 | **Portal 到 body 的浮层**（设置面板、Modal、部分菜单） | 层级按"视觉弹出层"判定，不按 DOM 位置；规则必须写全局作用域 |
| 2 | **同屏分区**（轨迹详情面板、侧栏窗格） | 不是弹出，归 L0 常驻分区，用"玻璃卡"配方而非"菜单"配方 |
| 3 | **原生控件不可样式化**（select 下拉） | 用 JS 自定义渲染（如版本选择器），层级语义不变（仍算 L2） |
| 4 | **语义色单元**（蓝发送键、绿运行中、红错误、黄警告） | 层级规则照常，颜色永不改 |
| 5 | **深色模式** | 全局豁免（只动浅色），层级架构不区分深浅 |
| 6 | **收起模式** | 同一单元的另一形态（rail 变形），层级不变，规则随 `.hHd-Xa_collapsed` 兜底 |
| 7 | **点击跳转类**（详情标题跳转按钮） | 无浮层，属于 L0 单元的行为扩展（JS 转发），不产生新层 |
| 8 | **选中态（aria/data 属性）** | 属于 L0 的"第三种状态"，与悬停同级处理（同一变量） |
| 9 | **特异性陷阱**（豁免链长度） | 每单元规则块注明"必须与常驻规则同长豁免链"，防止层级规则互压 |
| 10 | **JS 补丁类**（占位符、点击外关闭、自定义下拉） | 记入对应单元的"行为层"，与样式层分开注记 |

## 六、可行性结论

1. **模型成立**：40+ 单元全部落入矩阵，无游离；分界面与代码分区一一对应。
2. **改动的查找成本**：从"全文搜类名"降为"分区 → 单元 → 层级"三步定位。
3. **改动的执行成本**：同层配方变量化后，整层修改 = 一行变量；单点修改 = 一个规则块。
4. **风险**：层级标记与变量化需逐块标注（机械工作，零行为变更）；特例清单需随新元素持续更新。

## 七、建议落地顺序（后续工作）

1. 给全部规则块注释补 `L0/L1/L2` 标记（纯注释，零风险）；
2. 把同层配方提炼成 `--kaguya-*` 变量并逐块替换（先做 L1 菜单层试点）；
3. 设计规范.md 与本文档合并成"总索引"（surface → 单元 → 层级 → 规则块行号）。

## 八、深度可行性分析（往深了想）

### 8.1 模型与现实的四个错位（必须提前承认）

1. **CSS 本身没有"菜单层级"概念**——层级是应用 DOM/JS 的现实，我们的分类是对现实的**映射**而非约束。映射错位的风险永远存在：新增的官方浮层可能既不叫菜单也不在我们预料的位置。因此模型定位是"索引工具"，不是"运行时机制"。
2. **"同层同配方"是弱约束**。现实中同层元素配方已经分化（L1 菜单 78%/55%，Cordis 面板 85%/65%，版本下拉又是第三种）。正确表述应是：**层提供默认配方（变量），特例显式覆盖**——默认+覆盖，而不是绝对统一。
3. **行为层无法变量化**。占位符改写、点击外关闭、自定义下拉、点击转发这些 JS 块各有各的生命周期，没有"层级变量"可共享。方案能简化的是**样式层**；行为层只能靠"分块注记 + 编号清单"管理。若过度承诺"一处改全部生效"，会重演悬停色那种"改了没生效"的信任危机。
4. **特异性/层叠事故无法被架构消灭，只能被模板化**。这两天三次悬停失效，根因都是豁免链长度（特异性）。深想后的解法：**每层建立"基线规则模板"**（固定豁免链、固定书写顺序、固定 !important 策略），所有同层规则从模板复制——把随机事故变成模板事故，模板一旦对了就永远对。

### 8.2 必须配套的三个机制（否则方案不可持续）

1. **类名契约清单**：官方哈希类名（hHd-Xa_*、Y0dWHa_*、Nqubda_*…）是整套映射的地基，官方一升级全失效。方案应维护"单元 → 依赖类名 → 官方包出处"的契约表，升级前 diff 一次。
2. **自检徽章（轻量回归）**：皮肤启动时检查关键类名是否在 DOM 里存在 + 展示版本号（曾做过的 🌸 徽章思路，以更轻的形式回归）。任何"突然全白"都能 3 秒内判定是缓存、类名失效还是皮肤未加载。
3. **变量带版本号**：改配色时新增 `--kaguya-l1-panel-v2` 而不是覆盖旧变量——**变量本身就是快照，改色=换版本，回退=改回变量名**，天然可逆。

### 8.3 性能与安全边界

- 分区注释、变量化：零运行开销；
- 真正的性能大头是 backdrop-filter 的层数——层配方表正好能用来审计"每层用了多少 blur"，超标时优先降层；
- JS 补丁（MutationObserver、全局点击监听）数量要设上限（建议 ≤8 个），每加一个都记入行为清单，避免监听器互相打架。

## 九、应急预案（分五级）

### P1 · "改了没生效"（最常见，本工程已踩 3 次）

排查顺序（做成清单贴在规范里）：
1. **加载检查**：浏览器是否真的加载了新包（版本徽章/包大小对比）；
2. **特异性检查**：新规则与同单元其它规则的 `:not` 链长度是否一致（差一个就翻车）；
3. **顺序检查**：同权重后写胜出，规则是否写在常驻规则之后；
4. **作用域检查**：元素是否 portal 到 body / 面板之外，选择器够不够得着；
5. **逐级回滚**：改回该块旧值 → 确认恢复正常 → 再查原因。

### P2 · 整皮肤失效（语法错 / MIME 错 / 体积上限——都真实发生过）

1. 自检脚本一条命令跑完：`node --check` 语法 + served 包长度对比 + data URI MIME 计数（应全为 image/webp）；
2. 立即回滚：三个快照按时间选——`bak-v10-std`（高清前）/ `bak-before-bg2`（换图前）/ `snap-20260818-layered`（层叠定稿）；
3. 若怀疑挂载问题：注释 cordis.patch.yml 行 → 重启 `dsh web` → 皮肤消失即证明是皮肤问题。

### P3 · 官方升级打坏类名

1. 先卸载皮肤验证（同上），确认是皮肤侧；
2. 按"类名契约清单"逐条 diff 官方包（我们已掌握核对方法：读官方 CSS 找新类名）；
3. 短期：`:where` 零特异性兜底 + 全局规则让新界面不至于全白直角；
4. 长期：更新契约表与规则块。

### P4 · 官方新增界面/按钮

1. 全局兜底自动接住（D 类按压 + :where 圆角），不会太难看；
2. 走"五步查找流程"补单元：定 surface → 定类名 → 定层级 → 补规则块 → 按层配默认变量；
3. 特例出现就记入特例清单（第八节的三机制兜底）。

### P5 · 行为层故障（JS 补丁失灵）

1. 症状区分：样式正常但交互没反应（如点击外不关闭）→ 定位到行为块而非样式块；
2. 行为块逐个停用排查（每个补丁都是独立 ctx.effect，可注释化）；
3. 回滚到上一行为版本（行为块与样式块分开注记后，可独立回退）。

### 回滚分级总表

| 级别 | 范围 | 手段 | 耗时 |
|---|---|---|---|
| R1 | 一个颜色/一条规则 | 改回变量/旧值 | 秒级 |
| R2 | 一个单元 | 恢复该规则块（快照提取） | 分钟级 |
| R3 | 一个界面（分区） | 恢复整个分区块 | 分钟级 |
| R4 | 全皮肤 | bak 快照覆盖 / git 检出 | 分钟级 |
| R5 | 挂载/环境 | 注释 patch 行 + 重启 dsh web | 分钟级 |

## 十、模型修正结论（一版定稿口径）

> **"水平×垂直绑定网络"作为索引架构成立，作为运行时机制不成立。**
> 定位与检索靠它（surface × 单元 × 层级 三键索引）；
> 统一修改靠"层默认变量 + 特例显式覆盖 + 变量版本号"；
> 稳定性靠"基线规则模板 + 类名契约清单 + 自检徽章"；
> 事故处理靠"五级预案 + 五级回滚"。

落地时不追求一次重构到位：先补层级注释（零风险）→ 再试点 L1 层变量化 → 用三机制验收 → 逐步推广。每一步都可独立回滚。
